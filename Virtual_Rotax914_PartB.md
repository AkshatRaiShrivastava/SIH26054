# Virtual Rotax 914 — Synthetic Data Generation Plan (Part B)

*Extracted from: SIH 2026 — DRDO Problem Statement 54, Virtual Rotax 914 Engine — Master Reference Document. Part A (problem statement) omitted; this file contains only the engine build data (sensor suite, mission phases, operating-parameter baselines, and data-generation architecture).*

## B.1 Purpose

This part specifies everything needed to build a virtual Rotax 914 engine that generates realistic, phase-aware, healthy synthetic sensor data — the data source the Digital Twin (DT) core, AI/ML layer, and dashboard consume during development and demonstration, before (or alongside) real telemetry becomes available. It maps directly onto the problem statement's required building blocks: the full sensor suite (B.2), mission-phase definitions and timing (B.3), the normal operating-parameter envelope for every phase (B.4), and the data-generation architecture that turns those baselines into a live, phase-consistent healthy engine (B.5).

*Note on “Injection Timing Parameters”: the Rotax 914 is carbureted, not fuel-injected — it has no injection timing to measure. This PS requirement is re-mapped to the 914's actual boost/mixture control hardware: wastegate/servo position feedback and enrichener solenoid state, which serve the same diagnostic purpose.*

## B.3 Mission Phases and Timing

A realistic virtual engine must behave differently depending on mission phase — RPM, MAP, temperatures, and fuel flow all change by phase. A representative MALE UAV mission profile runs roughly 14.5 hours total, dominated by the Loiter/ISR phase, which is the defining characteristic of a MALE endurance mission.

*For a hackathon-scale demo, running a real 14.5-hour simulation is impractical. Table 2 gives both the realistic duration (for architecture/validation discussions) and a compressed demo duration (a few minutes total) that preserves the same phase sequence and proportional emphasis on Loiter/ISR, so a complete mission can be shown live.*

## B.5 Virtual Engine Data-Generation Architecture

Data flow: Physical Engine Sensors (CAN/SocketCAN, ECU/TCU) + Avionics/GCS Telemetry (altitude, airspeed, OAT, mission mode) + Ground/Test-Rig Data (maintenance logs, fleet history) feed into Edge Data Acquisition & Pre-processing (sampling, filtering, unit normalization, timestamping). In simulation mode, the Synthetic Data Generator (this framework) replaces the physical-sensor input. It feeds a Physics-Based Thermodynamic & Performance Model (RPM-MAP-power maps, heat transfer, turbo/wastegate model) which exchanges state with an AI/ML Analytics Layer (anomaly detection, trend analysis) once the DT is monitoring live or replayed data. Together they produce the Synchronized Digital Twin State (virtual engine health index), which drives the Dashboard/HMI, Mission Replay & Post-Flight Analysis, and the Fleet-Level Health DB.

*The point of this architecture: the DT core, AI/ML layer, and dashboard downstream of pre-processing do not need to know or care whether the data is real or synthetic — in deployment, the same pipeline simply consumes real CAN/SocketCAN telemetry instead of the Synthetic Data Generator.*

### B.5.1 How Each Sensor Value Is Computed Each Timestep

- Phase base value — look up the nominal value (or range) for the current mission phase from Table 3 / Table 4 (e.g., RPM = 5,000 during Normal Cruise).

- Transient smoothing — apply a first-order lag (exponential smoothing) when transitioning between phases, so RPM/MAP/temperatures ramp realistically rather than stepping instantly (e.g., CHT should take minutes to rise on throttle-up, not be instantaneous).

- Physics coupling — derive dependent parameters from independent ones using the engine's own control-logic relationships — e.g., airbox temperature rises with MAP and ambient temperature; oil pressure is a function of RPM and oil temperature; EGT responds to AFR and load.

- Sensor noise — add small-amplitude, sensor-appropriate random noise (Gaussian for temperatures/pressures; quantization noise for digital tachometers) so the signal looks like real instrumentation, not a clean curve, while staying inside the healthy range for that phase.

- Environmental modulation — scale relevant parameters (airbox-temp cutback point, oxygen availability/EGT baseline, battery performance) based on the simulated altitude and OAT for that mission's environmental profile (cold-weather, hot-weather, high-altitude scenarios).

### B.5.2 Suggested Sampling & Data-Rate Tiers

- Tier 1 (high-rate, edge-only): vibration, knock — 1–10 kHz, processed on-edge into RMS/FFT features before transmission (raw waveform should not go over the telemetry link).

- Tier 2 (fast control-loop rate): RPM, MAP, throttle position, wastegate position — 10–100 Hz, matches typical SocketCAN frame rates for engine control parameters.

- Tier 3 (thermal/pressure rate): CHT, EGT, oil pressure/temp, fuel pressure/flow, airbox temp — 1–5 Hz, adequate since these parameters change on the order of seconds, not milliseconds.

- Tier 4 (slow trend rate): battery voltage/current, alternator output, ambient conditions — 0.1–1 Hz, sufficient for trend and state-of-charge tracking.

## B.6 Suggested Next Steps for the Build

- Implement the per-sensor generator functions (B.5.1) using Table 3 / Table 4 as the baseline — validate that a full compressed mission (Table 2) produces sensible, phase-consistent traces for every sensor in Table 1.

- Check that transitions between phases are smooth (no instant jumps) and that every value stays within its phase's healthy range — this healthy dataset is what everything downstream will be trained and calibrated against.

- Wire the generator into the dashboard/HMI to demo a live “mission in progress” rather than only static charts — this makes a much stronger live demonstration.

- Keep the sensor list in Table 1 versioned — as sensors are decided to be simulated vs. genuinely CAN-bus-read from a real test rig (if available), this table becomes the integration checklist.
